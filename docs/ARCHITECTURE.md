# معماری SAM 4.0

## اصل طراحی
SAM لایه‌ی تجربه، orchestration و هوشمندی است؛ هر دامنه تا حد امکان منبع داده‌ی مستقل و قابل تعویض دارد. اپلیکیشن نباید بدون قرارداد روشن، نسخه‌ی محلی را مرجع قطعی داده‌ی بیرونی فرض کند.

## لایه‌ها
1. **Presentation:** رابط Compose، فارسی/RTL، وضعیت صوت و اتصال.
2. **Application:** use caseها، فرمان‌ها، مجوزها و گردش کار.
3. **Domain:** مدل‌های مستقل از provider برای وظایف، یادداشت، تقویم و تولید.
4. **Integration:** adapterهای رسمی سرویس‌ها، OAuth، rate limit و retry.
5. **Local resilience:** cache، outbox، sync cursor، شناسه‌های خارجی و ثبت تغییرات.
6. **Security:** Android Keystore، حداقل مجوزها، حذف secrets از مخزن.

## سیاست همگام‌سازی
- هر provider قابلیت‌های خواندن/نوشتن و جهت sync مخصوص خود را اعلام می‌کند.
- عملیات نوشتن ابتدا در outbox ثبت و سپس با idempotency مناسب ارسال می‌شوند.
- تعارض‌ها با timestamp به‌تنهایی حل نمی‌شوند؛ سیاست هر دامنه باید مشخص باشد.
- قطع اتصال نباید باعث ادعای موفقیت عملیات remote شود.

## کاندیدهای اتصال
Notion (دانش و یادداشت)، TickTick (وظایف)، Google Calendar (تقویم)، Google Drive (اسناد/پشتیبان)، و یک سامانه‌ی مناسب برای داده‌های تولید. انتخاب Airtable یا ERPNext منوط به بررسی API رسمی، هزینه و میزبانی است. برای حسابداری شخصی نیز API رسمی باید بررسی شود؛ CSV می‌تواند مسیر جایگزین باشد.

کتابخانه‌های صوتی فارسی ممکن است صرفاً از طریق deep link و metadata دستی قابل اتصال باشند، مگر API عمومی معتبر در دسترس باشد.

## صوت و آفلاین
STT، TTS، تشخیص wake word و مدل محلی اجزای مستقل‌اند. هر قابلیت باید ماتریس online/offline و مجوزهای خود را داشته باشد. wake word پس‌زمینه تا آزمون روی دستگاه هدف تأییدشده نیست.
